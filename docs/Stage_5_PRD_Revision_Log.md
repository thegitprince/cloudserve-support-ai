## 5. The reflection

**What did you most misunderstand about the problem when you wrote version one?**
That classification accuracy and governance safety were effectively the same problem, solved by the same mechanism — the deterministic `MANDATORY_ESCALATION_INTENTS` lookup table. They are not. The table is only as trustworthy as the label it is given, and a classification error that crosses the mandatory/discretionary boundary defeats it silently, with no error raised anywhere, because the table did exactly what it was asked to do with the information it was given. Version one treated FR-04's lookup table as the authoritative safety mechanism on its own; it needed a second, content-based, classification-independent check from the start, not as a reactive fix after a live policy breach.

**Which piece of discovery work would have caught it earlier?**
None of it, directly — no stakeholder interview or dataset field names this failure mode, because it is a property of the *system's own* classification behavior under ambiguity, not something visible in the historical ticket data before a system existed to misclassify anything. It only became visible empirically, during the live 80-ticket validation gate, when one specific ticket happened to sit exactly on the `api_key_issue` / `security_incident` boundary. A deliberately adversarial test set of "boundary" tickets — written to sit ambiguously between one mandatory and one discretionary intent — does not exist in the current dataset and would likely have surfaced this in Stage 3 or 4 instead of Stage 5.

**What would you do differently if you started this project again on Monday?**
Build the content-based safety net (now FR-12) at the same time as FR-04's lookup table, as a first-class design assumption — "the classifier can put a ticket in the wrong bucket, and the mandatory/discretionary boundary is exactly where that's most dangerous" — rather than discovering it empirically after a real breach in validation.

**What is still uncertain, and what would you need to resolve it?**
(a) Whether the measured 93.8% classification accuracy and 5.3-point calibration gap generalize to the hidden 120-ticket set — not yet tested, by design, per `Evaluation_Framework.md`'s "go to the test set once" rule; resolved only by that one run, when it happens. (b) Whether `HIGH_RISK_KEYWORDS`' small, literal 9-term list has an acceptable false-negative rate against phrasings that describe a real breach/compromise without using any of those exact substrings — would need a broader adversarial-phrasing test set, which does not currently exist, to resolve properly. (c) Whether the `standard`-tier and `latin_america` FCR gaps (`docs/Fairness_Audit.md`) are a real, persistent fairness issue or validation-set sampling noise, given the thin segment sizes involved (n=42 and n=7 respectively) — would need either a larger segment sample or the hidden set's own segment breakdown to tell apart.
